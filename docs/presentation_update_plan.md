## 3. 사용자가 채워야 할 빈칸 (PM이 만들 수 없는 것)
1. 발표일, 시연 방식(실시간/녹화)과 시연 계정
2. 테스트에 참여한 인원 수(설문 응답 수 + 앱 피드백 2건)
3. **외부 테스터 설문 응답 요약**(응답 수, 완료율, 만족도 중앙값, 반복된 의견). 원문은 올리지 않는다
4. 회고 사례 캡처(회고 → 튜터 답변에 반영된 장면), 튜터 답변 화면 캡처
5. 팀원별 한 줄 회고
6. 팀 명단에서 "이창민"을 "이창민조장"으로 표기할지

## 4. 정직성 점검 (평가에서 문제가 될 수 있는 부분)
- 피드백 대부분이 **팀 내부 인수 테스트**에서 나왔다는 사실을 숨기지 않는다(`feedback_to_improvement_map.md` 5행의 원칙). 외부 테스터 근거는 설문 응답이 확인된 만큼만 쓴다.
- 앱 안 피드백은 **2건**뿐이다. 건수를 부풀리지 않는다.
- CR-019, 020, 021②~④, 023, 024, 025, 027은 아직 구현되지 않았다. "개선했다"가 아니라 "계획했다/향후"로 표시한다. 구현·배포 확인 전에는 "완료"라고 쓰지 않는다(변경관리 운영 규칙 4).
- 배포 환경에서 직접 확인하지 못한 항목(CR-014, 015, 022 화면)은 push·배포 뒤 확인하고 쓴다.

## 5. 진행 순서 제안
1. 사용자가 §3 의 1~6을 준비하는 동안 PM 은 승인된 변경(§1, §2 의 높음)만 슬라이드에 반영한다.
2. CR-028, CR-026 이 끝나고 push·배포가 되면 배포 슬라이드(11번)와 개선 슬라이드(14번)의 수치를 갱신한다.
3. 설문 응답 요약을 받으면 결과(13번)와 사용자 테스트(12번)를 채운다.
4. 마지막에 테스트 수를 다시 실행한 값으로 갱신하고, 슬라이드 전체를 한 번 읽어 CR 상태와 어긋난 표현이 없는지 점검한다.
