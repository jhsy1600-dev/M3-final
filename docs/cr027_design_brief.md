# CR-027 디자인팀 브리프: 전체 화면 색상 개편

작성: PM, 2026-11-23. 근거: 변경관리 CR-027(`docs/change_management.md`). 사용자 요청(2026-11-23): **모든 화면, 화면 틀(레이아웃)은 그대로 두고 색상만 바꿔 조금 참신하고 눈에 잘 들어오게** 해서 사용자의 느낌과 사용 중 인지 정도를 높인다.

## 1. 목표와 범위
- 대상: 학습자 화면 전부(첫 동의 모달, 대시보드, 학습 경로 설정, 학습 과제 계획, 학습 실행 기록, 종합 학습 분석, AI 튜터, 내 정보·설정)와 관리자 화면 3개(사용자 관리, 참고자료 관리, 사용자 피드백).
- **바꾸는 것: 색(배경, 글자, 테두리, 강조, 상태 표시, 그림자 색)만.** 필요하면 색과 함께 가는 요소(그림자 농도, 아이콘 색)까지.
- **바꾸지 않는 것:** 요소의 위치·순서·크기·간격, 글자 크기, 글꼴, 문구, 화면 흐름, 요소 추가·삭제. 레이아웃을 바꾸고 싶은 아이디어는 결과물에 "제안"으로 따로 적는다(이번 적용 대상이 아니다).

## 2. 지켜야 할 고정 규칙 (어기면 되돌린다)
1. **글자 대비:** 본문·라벨은 배경 대비 4.5:1 이상, 큰 글자(24px 이상)와 아이콘은 3:1 이상. 대비 값을 표로 적는다.
2. **색만으로 구분하지 않는다:** 상태(완료, 진행, 오류)는 색과 함께 글자나 모양이 이미 있으며, 색을 바꿔도 서로 구별되어야 한다(적록 색약 시뮬레이션에서 구별). 빨강/초록만으로 짝을 짓지 않는다(파랑/주황 권장).
3. **의미 있는 색:** 오류와 경고는 빨강 계열 또는 주황 계열, 완료는 초록 계열 등 **의미가 통하는 색을 유지**한다. **추천 요일, 이번 주 과제, 기록이 없는 날 같은 "놓칠 수 있는 것"에는 빨강·경고색을 쓰지 않는다**(핵심 결정: 놓쳐도 연체·실패·이월이 아님).
4. **AI 생성 표시와 동의 안내는 눈에 띄는 상태를 유지**한다(미션 요건: AI 생성 콘텐츠임을 명시). 흐리게 만들지 않는다.
5. **글자 크기 하한(CR-015):** 이번 변경은 글자 크기를 건드리지 않는다. 색 때문에 읽기 어려워 보이는 곳이 있으면 대비를 올려서 해결한다.
6. 지원 폭: 넓은 화면(1280 이상), 태블릿(768), 휴대폰(390) 3종에서 확인한다. 다크 모드는 이번 범위가 아니다(만들지 않는다).
7. 수준은 번호가 아니라 서술형 라벨이므로, 수준을 색 단계(점수처럼 진해지는 색)로 표현하지 않는다(핵심 결정: 번호·점수·비교에 쓰지 않음).

## 3. 현재 색 구조 (작업 전에 알아야 할 사실)
- 색 변수 12개가 `:root` 에 있다(목업과 실제 CSS가 같은 이름): `--ink #20263a`(본문 글자) `--muted #7d8498`(보조 글자) `--line #e9eaf1`(테두리) `--bg #f6f7fb`(배경) `--white` `--blue #4c62dc`(주 강조) `--blue-dark #3549bd` `--lav #eef0ff`(연한 강조 배경) `--purple #8064d7` `--green #289b7a` `--orange #e7a34b` `--red #dc6974`, 그림자 색 `rgba(39,48,85,.055)`.
- **변수를 거치지 않고 직접 쓴 색 값이 실제 CSS에 193곳(고유 122개), 목업에 172곳 있다.** 따라서 `:root` 변수만 바꾸면 일부가 옛 색으로 남는다. 결과물에는 **옛 색 → 새 색 대응표**(고유 값 전부)를 포함해야 개발팀이 기계적으로 옮길 수 있다(CR-015 때 쓴 방식).
- 실제 앱에는 목업에 없는 요소가 있다(수준 콤보박스, 튜터 말풍선, 동의 체크, 대화 목록 항목 등). 이 요소의 색은 목업에서 보이지 않으므로 대응표에 "실제 앱 전용 클래스" 항목으로 표시하고, 필요하면 PM이 앱 캡처를 따로 준다.

## 4. 결과물 (이 세 가지를 모두 제출)
1. **수정 목업:** `mockup/index_redesign.html`(복사본). 표준 목업 `mockup/index.html` 은 PM 승인 전에 덮어쓰지 않는다. 화면 11개 전부 반영.
2. **색 대응표:** 옛 값 → 새 값(변수 이름이 있으면 변수 이름 포함), 쓰임(어디에 쓰는 색인가), 대비 값(글자색이면 배경과의 비율). 표는 `docs/cr027_color_mapping.md` 로 저장.
3. **화면 캡처 비교:** 화면 11개 × 3폭의 이전/이후 비교(최소한 대표 화면 5개 × 3폭). 색 때문에 읽기 어려워진 곳이 없는지 점검 결과를 적는다.
- 설계 의도(왜 이 색인지, 한 단락)와, 이번 범위 밖의 레이아웃 제안(있으면)을 `docs/cr027_color_mapping.md` 앞부분에 적는다.

## 5. 이후 단계 (디자인팀이 알아 둘 것)
1. PM 이 결과물을 확인하고 고정 규칙(2장) 위반을 점검한다(대비 계산, 색약 시뮬레이션, 의미 있는 색, AI 표시).
2. 승인되면 PM 이 표준 목업을 갱신하고 개발 지시서를 낸다. 개발팀은 (가) 직접 쓴 색 값을 변수로 정리하는 작업(화면 변화 없음)을 먼저 하고, (나) 변수 값과 대응표대로 새 색을 적용한다. 이 두 단계로 나누면 실수를 줄이고 되돌리기 쉽다.
3. 완료는 PM 이 배포 환경에서 직접 확인한 뒤에만 쓴다(미확인은 "미검증"으로 남긴다).
